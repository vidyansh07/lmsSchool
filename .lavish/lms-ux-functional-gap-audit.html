Functional contract for every high-volume page

A “feature-rich” screen is not one with more controls. It lets a user find, understand, act, recover and repeat with confidence.

1
Find

Search, meaningful filters, saved views, URL state, sort and pagination.

2
Understand

Identity, scope, status, provenance, counts and a clear canonical record.

3
Act

One primary action, capability-aware secondary actions, validation and visible busy state.

4
Recover

Retry, request ID, preserved input, unsaved-change guard and reversible choices.

5
Trust

Impact preview, confirmation proportional to risk, exact export parity, audit history and no role/profile contradictions.

Trainer onboarding acceptance criteria

  2. Partial User and trainer profile creation is atomic. Invitation delivery status/recovery is not yet surfaced.

  8. Not fixed Invitation status, resend and mail-failure distinction are not present in the hub.

Implemented and remaining

Still open: full capability-diff preview, optimistic concurrency for ordinary admin edits, and any deliberate persona-conversion wizard.

Identity

Profile invariants

A user must never report profile_type=trainer with a student profile ID. An archived legacy profile may retain history but cannot silently grant current access.

Concurrency

Stale edits

Account and role forms need version/updated-at checks. On conflict, show what changed and let the operator reload—not a generic save failure.

Recovery

Partial side effects

Invitation/email failures, audit writes and session revocation need explicit outcomes. The UI must distinguish “record created; email failed” from “creation failed.”

Implementation sequence

Fix integrity first, then discoverability, then breadth

This sequencing avoids polishing workflows whose underlying identity contract is still unsafe. It is intentionally not a commitment to implement all 28 findings.

Owner decisions

Three choices that should not be guessed in code

The audit has a recommendation for each, but these change product behavior or governance and should be explicitly accepted.

Adopted

Can one person hold multiple personas?

Implemented: one primary authorization role; an optional teaching profile for Manager; direct student/trainer persona conversion is blocked.

  • Prevents accidental privilege loss.
  • Preserves history without treating stale profiles as current.
  • Allows a manager to teach without becoming a trainer-role account.
Partially adopted

Where is the canonical people record?

Implemented for discovery: the trainer hub is canonical and account pages link to domain profiles.

  • The duplicate trainer route redirects.
  • Trainer rows open the review record.
  • Full profile/account/audit tabs remain open.
Decision open

Manager versus Counsellor

Still recommended: explicitly specialize navigation and saved queues even if many backend capabilities remain shared.

  • Manager: staffing, delivery, review, academic operations.
  • Counsellor: pipeline, fees, follow-up, communication, student care.
  • Document any intentional overlap as policy.
